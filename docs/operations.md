# 会計・レジ・電子カルテ・アクセス管理

予約運用に追加した4つの機能の使い方と、データベース導入・確認手順です。各画面は `/{tenantSlug}/...` にあり、選択中のテナント・店舗のデータを扱います。

| 機能 | 画面 | 主な用途 |
| --- | --- | --- |
| 会計 | `/checkout` | 予約ごとの明細、入金内訳、全額取消・返金記録、会計控え |
| レジ締め | `/register` | 開店現金、現金の入出金、実査差額、締め日報 |
| 電子カルテ | `/charts` | 予約に紐づく施術記録、前後写真、確定・訂正履歴 |
| スタッフ権限 | `/access` | ログイン利用者の招待、役割・操作権限・利用店舗の設定 |

## 1. 会計

会計は、店舗または外部サービスで受領済みの入金・実施済みの返金を記録します。この画面からカード決済、振込、Stripeなどの決済サービス（PSP）への請求・返金は実行しません。会員アプリの決済・ポイント・クーポンとも自動連携していません。

### 会計を確定する

1. レジ担当者が、本日の店舗レジを開店します。現金以外の会計でも営業中のレジを選択します。
2. 会計一覧または予約から対象予約の会計を開きます。同じ予約の有効な会計があれば、その記録を使います。
3. 下書きの明細名、数量、税込単価、値引額、税率を確認します。初期明細は登録メニューから作られます。値引額は明細全体に適用され、税率は0・8・10%を選べます。内税は会計全体の税率ごとに計算し、端数を切り捨てます。
4. ポイントを利用する場合は、円換算した「ポイント利用額（円）」を入力します。通常値引き後の金額から差し引き、売上と支払額が同額減ります。複数明細には通常値引き後の金額比で整数配分し、端数は余りの大きい明細（同率は表示順）へ配分します。内税もポイント値引き後の金額で計算します。ポイント残高の消費・返還は会員アプリ等で別途記録してください。
5. 実際に受領した金額を、現金・カード・振込・確認済みの事前入金・その他に分けて入力します。内訳の合計を会計金額と一致させます。カード等は外部での受領確認後に記録します。
6. 変更を下書き保存し、本日の営業レジを選んで会計を確定します。予約の支払状況は `PAID` に更新され、現金分だけがレジ現金の増加として記録されます。予約の来店・施術完了状態は別に管理します。
7. 確定後は「会計控え・印刷」から、保存済みの明細・税額・支払内訳を表示してブラウザで印刷できます。

確定済み会計の明細は直接編集できません。下書き作成後に予約の顧客・メニュー・担当者・日時が変わった場合は確定を止めます。「予約に合わせて下書きを作り直す」は最新予約を取り込み、明細・通常値引・ポイント値引・支払内訳を初期化する操作です。

### 全額取消・返金記録

お客様への全額返金と利用ポイントの返還を店舗・決済端末・外部サービスで完了した後、確定会計の「全額取消・返金記録」に理由を入力し、「全額返金・利用ポイントの返還を確認しました」を選択して記録します。現金分は選択した本日の営業レジから差し引かれ、予約の支払状況は `REFUNDED` になります。現金が不足する場合は記録できません。

これは全額取消の記録です。部分返金、外部への返金実行、確定明細の直接修正には対応していません。金額訂正が必要な場合は元の会計を全額取消してから、同じ予約の新しい会計を作成します。元記録と訂正元への紐づきは残ります。過去日の会計を本日のレジで取消しても、過去の締め日報は書き換えず、本日の取消に計上します。

### 管理者メールへの通知

基本設定の「予約受付」で、店舗ごとの「管理者メール」と「予約・会計メール通知」を設定します。有効な通知先とON設定が揃った場合だけ送信します。

- 新規予約: お客様名、日時・所要時間、メニュー、担当・指名有無、予約金額（予定）、予約経路・状態・支払状況を通知します。ポイント利用と確定売上は会計時に確認します。
- 会計確定: お客様名、予約日時・メニュー・担当、税込小計、通常値引き、ポイント利用値引き、確定売上・内税、受領済みの支払内訳を通知します。
- 会計取消: 取消した金額とポイント値引き、返金記録の内訳を通知します。ポイント残高の返還は自動実行しません。

通知内容は操作時に保存し、後日の顧客・メニュー変更で変わりません。予約番号・会計番号と管理画面リンクで対象を確認できます。電話番号、メールアドレス、自由記入のメモ、支払確認番号は本文に含めません。会計確定・取消と通知キューの保存は同一トランザクションで行い、同じ操作の再送でキューを重複作成しません。SESへの送信は非同期で再試行され、送信完了は受信箱への到着確認とは別です。

### 既存の入金済み予約

以前の予約にある `PAID` は、明細・金額・税額・受領方法まで確認できる会計記録ではありません。新しい会計への自動変換は行いません。

- 過去の領収書や外部決済記録と照合し、初期明細の金額を確認・修正します。現在の登録メニュー価格が、当時の入金額と同じとは限りません。
- `PAID` の予約は、全額を「確認済みの事前入金」として登録します。確認番号または確認内容を記入し、「既存の事前入金を確認しました」を選びます。追加の現金・カード回収を記録して二重計上することはできません。
- 通常の未払い予約でも、事前入金の内訳がある場合は確認内容と確認チェックが必要です。
- 過去入金を本日のレジに記録すると、本日の会計記録・日報に含まれます。当時の日報を自動復元する処理ではありません。

顧客利用額の新しい集計は、確定済みの会計金額を基準にし、全額取消済みを除外します。旧予約の `PAID` や旧顧客利用額から新会計を推定生成する処理はありません。

## 2. レジ開店・入出金・締め

基本の順序は「レジ開店 → 会計・現金入出金 → 実査 → レジ締め」です。

1. `/register/new` で開店時の釣銭・レジ現金を入力して開店します。店舗に営業中のレジが残っている場合や、その営業日が登録済みの場合は新たに開店できません。
2. 営業中は、会計に関係しない現金の入金・出金を、金額と理由付きで記録します。会計の現金分・現金返金は、会計確定・全額取消から自動で記録されます。別途手入力して二重計上しないでください。
3. 営業終了時に現金を実際に数え、「実査現金」と締めメモを入力して締めます。
4. 締め後は想定現金・実査現金・差額、会計件数・取消件数、売上・取消・正味金額、支払方法別内訳を保存した締め日報として閲覧します。

想定現金は「開店現金 ＋ 現金会計 ＋ 手動入金 − 手動出金 − 現金返金」です。カード・振込・事前入金は会計集計に含まれますが、レジ現金には加算されません。差額は「実査現金 − 想定現金」です。

締め済みのレジへの会計・入出金追加、締めの直接変更、同日の再開店はできません。前日の未締めレジがあれば、そのレジを締めてから本日の開店を行います。会計確定・取消で使えるのは本日の営業レジです。営業日はAPIで店舗のタイムゾーンから判定します。

開店画面も選択中の店舗のタイムゾーンで営業日を表示します。月報、会計を伴わない在庫管理、外部決済端末への接続はこの機能に含まれません。

## 3. 電子カルテ

予約ごとに1つのカルテを作成します。顧客・担当者・予約メニュー・予約日時は、対象店舗の予約からサーバーで取得し、カルテ作成時の情報として保持します。一般の顧客メモとは別の記録です。予約・顧客情報からのリンク、または `/charts/new` の予約検索で作成できます。顧客・予約ごとの一覧絞り込みも使えます。

### 下書き・確定・訂正

1. 施術日時、部位、実施した施術の詳細、使用機器、照射出力（J）、パルス幅、肌の観察記録、使用製品・材料、アフターケア、次回来店の予定を下書きに入力します。出力・パルス幅は実施時の設定値・単位を文章として記録する欄で、推奨値の計算はしません。
2. 下書きを保存し、内容と写真を確認してカルテを確定します。確定には施術詳細の入力が必要です。
3. 確定後に変更が必要な場合は訂正理由を入力し、次の版の下書きを作成します。元の確定版を保持したまま、内容・写真を引き継ぎます。訂正版を保存して確定すると、旧版の内容、写真、確定者・日時、訂正理由を履歴で確認できます。

確定版の本文・写真は直接変更できません。下書きも含め、カルテがある予約の顧客・メニュー・担当者・日時は予約編集から変更できません。カルテの確定は、会計確定・入金・予約の施術完了処理を代行しません。

別の操作で更新された場合は競合として保存を止めます。最新情報を取得すると、最新の本文を表示し、未保存入力は別に保持します。双方を確認し、必要な場合だけ入力を下書きへ戻して保存します。新規作成中に別の予約へ切り替える場合は、旧予約の施術入力を引き継がず初期化します。

### 施術前後の写真

- JPEG・PNG・WebP、1枚5MiB以下、1つの版につき合計10枚までです。最大24メガピクセル、幅・高さは各16,384ピクセル以下、アニメーション非対応です。サーバーで実画像をデコードして検証します。
- カメラの向きを補正し、EXIF・GPS等の画像メタデータを除去して同じ形式に再保存します。JPEGは品質95で再符号化します。保存用画像が5MiBを超える場合は、サイズを小さくして選び直します。
- 新しく追加する写真は非公開の Google Cloud Storage に保存し、DBには保存先・世代番号と写真情報だけを保持します。認証・テナント・店舗・カルテ閲覧権限を毎回確認するAPI経由で表示し、公開URL・ダウンロードトークン・署名URLは発行しません。応答をキャッシュしません。
- 施術前／施術後に分け、部位（120文字まで）、撮影日時、脱毛・肌の状態メモ（1,000文字まで）を写真に添付できます。写真を選んで「写真を保存」を押すと保存されます。写真は拡大表示できます。
- 新規アップロードにはAPI側の `CHART_PHOTOS_BUCKET` と実行サービスアカウントのバケット権限が必要です。未設定・接続失敗時はエラーを返し、DBへの画像保存に切り替えません。設定手順は [infrastructure.md](infrastructure.md#private-chart-photo-storage) を参照してください。
- 過去にDB保存した写真は従来の認証経路で読み出せます。自動移行は行いません。Cloud Storageのオブジェクトは記録した世代番号を指定して取得・削除し、別の画像への上書きを避けます。
- 追加・削除は最新の下書きに対して行います。訂正版で写真を削除しても、以前の確定版に紐づく写真は残ります。参照がなくなった画像は非表示にし、クラウドの削除に失敗した場合は削除待ち情報を残して以後の写真追加・削除時に再試行します。
- クラウドへの保存成功後にDB更新が競合で拒否された場合は、未参照を確認して削除します。通信障害でDBコミットの成否が不明な場合は写真を失わないよう残し、運用者が記録と照合します。アップロードの応答自体が失われた場合も、非公開オブジェクトが残ることがあります。
- 写真の部位・状態メモはURL・監査ログに記録しません。アップロード時の専用メタデータヘッダーにも施術情報が含まれるため、追加するプロキシ／APMでもリクエストヘッダー全文を記録しないでください。
- カルテ一覧と操作履歴には、写真データや施術本文を載せません。

## 4. スタッフ権限・招待・操作履歴

`/access` はシステムにログインする利用者の管理です。予約に割り当てるスタッフ名簿 `/staff` の登録とは別で、名簿を作ってもログイン権限は付与されません。

### 招待する

1. 「スタッフを招待」で、招待先メールアドレス、役割、利用できる店舗、操作権限、有効期間を指定します。画面の有効期間は1・3・7日から選択できます。
2. 発行直後に表示された招待リンクをコピーし、管理者が本人に共有します。招待メールは自動送信されません。
3. 本人が招待先と同じメール確認済みのアカウントでログインし、リンクから承諾すると、そのテナントのメンバーになります。

リンクは一度だけ承諾できます。期限切れ・取消済み・承諾済みは使用できず、承諾時にも招待者の現在の権限を確認します。元トークンは保存しないため、発行画面を閉じた後に同じリンクを再表示することはできません。必要なら同じメールへ再発行します。このとき以前の未承諾招待は取り消されます。

承諾済み招待は取り消せません。利用を止める場合はメンバーの利用状態を「利用停止」にします。これは対象テナントへのアクセス停止で、ログインアカウントの削除ではありません。

### 役割・操作権限・店舗制限

以下は個別設定を使わない場合の既定値です。

| 役割 | 既定の操作範囲 |
| --- | --- |
| オーナー `OWNER` | 全店舗・全機能。個別制限なし |
| 管理者 `ADMIN` | 全操作。自身に許可された店舗・権限の範囲で利用者を管理 |
| 店舗責任者 `MANAGER` | 権限管理以外。返金記録・レジ開閉・操作履歴を含む |
| スタッフ `STAFF` | 各業務の閲覧、予約・顧客・会計・カルテの登録変更。返金記録・レジ開閉・操作履歴の閲覧は既定で含まない |
| 閲覧のみ `VIEWER` | 各業務の閲覧。操作履歴の閲覧は既定で含まない。更新は許可できない |

個別設定では閲覧・変更・返金記録・レジ開閉などを分けて指定できます。変更を許可すると同機能の閲覧も許可されます。`access.manage` を持てるのはオーナー・管理者だけです。

| 操作 | 必要な権限 |
| --- | --- |
| 会計閲覧／下書き作成・保存・確定／全額取消 | `checkout.read`／`checkout.write`／`checkout.refund` |
| レジ閲覧／開店・手動入出金・締め | `register.read`／`register.close` |
| カルテ・写真閲覧／作成・保存・確定・訂正・写真変更 | `chart.read`／`chart.write` |
| 招待・メンバー権限管理／操作履歴閲覧 | `access.manage`／`audit.read` |

個別設定で会計の確定・全額取消を任せる場合は、営業レジを選択するため `register.read` も付与します。レジを開店・締める権限とは別です。予約候補を一覧から選ぶには `reservation.read` が必要で、許可されていない場合は予約番号を指定して会計を開始します。カルテの閲覧のみでは本文・写真を表示し、作成・保存・確定・訂正・写真変更の操作は表示しません。

オーナー以外は利用店舗を限定できます。店舗指定なしは全店舗です。管理者は自身の権限・店舗範囲を超える付与やメンバー管理はできず、オーナーの管理はオーナーが行います。自分自身の権限・利用状態の変更、最後の有効なオーナーの降格・停止は禁止します。URL・店舗選択だけで権限は得られず、APIでも権限・テナント・店舗範囲を検証します。

### 操作履歴

`/access/audit` では日時、操作者、操作名、対象、接続元IPを確認できます。操作名で検索でき、100件ずつ追加取得します。店舗制限のある利用者には選択中の店舗に紐づく履歴だけを返します。店舗情報を持たない招待・権限変更履歴は、その店舗限定の一覧には表示されません。

## データベースへの導入

この変更は会計・レジ・カルテの新しいテーブル、既存メンバー・招待の権限／店舗範囲列、予約の複合一意制約などを加えます。既存の予約・顧客・スタッフ・メニュー・写真・入金を、新しい業務記録へ自動移行するバッチはありません。

1. 対象データベースと接続設定を確認し、既存データのバックアップを取得して復元手順を確認します。写真の実体はCloud Storageにあるため、DBのバックアップだけでは復元できません。バケットの復旧設定と、DBの写真情報・オブジェクト世代番号を対応させた復元手順も用意します。既存のDB保存写真はDBバックアップに含まれます。
2. 本番データを複製した検証環境でスキーマ差分と既存データの保持を確認します。既存メンバーの `useCustomPermissions=false` は役割の既定権限、`salonIds=[]` は全店舗になるため、導入後の権限・店舗範囲も見直します。
3. 適用するコード・スキーマを揃えて、接続先を確認した上で生成・適用します。

```bash
npm install
npm run db:generate
npm run db:push
```

データ損失を示す警告があれば適用を止め、差分を確認します。`--accept-data-loss` を付けて警告を無条件に通さないでください。これらのコマンドは接続先に作用するため、検証用・本番用の `DATABASE_URL` を取り違えないようにします。

4. API・Webを同じ更新版で起動し、役割別ログイン、店舗切替、旧予約の表示、新規会計、レジ開閉、カルテ保存、招待・停止を確認します。
5. 旧 `PAID` 予約は会計記録と別に照合します。過去入金・利用額を自動生成済みと見なさないでください。

データの分離とログインの前提は [tenancy.md](tenancy.md)、初回オーナー登録は [provisioning.md](provisioning.md)、本番接続は [infrastructure.md](infrastructure.md) を参照してください。

## 開発時の確認

リポジトリルートで型チェックと、データベース不要のテストを実行できます。

```bash
npm run typecheck
npm run test:operations
```

実PostgreSQLを使うテストは、ローカルの使い捨て専用データベースにだけ実行します。環境変数は `OPERATIONS_TEST_DATABASE_URL` です。データベース名を `_test` で終わる名前にし、通常利用・本番データベースを指定しないでください。カルテの結合テストは接続先がループバックであることも確認します。

```bash
export OPERATIONS_TEST_DATABASE_URL='postgresql://USER:PASSWORD@127.0.0.1:5432/salonops_operations_test'
DATABASE_URL="$OPERATIONS_TEST_DATABASE_URL" npm run db:push
npm run test:operations:db
```

結合テストは明示した専用データベースへ試験用テナント・利用者を作成して確認し、自分の試験データを清掃します。環境変数未指定では実DBテストをスキップするため、スキップを保存処理の成功と扱わないでください。会計・アクセス・既存API権限・カルテの境界と保存を確認し、カルテの同時更新、確定不変性、写真制限・履歴保持も検証します。

型チェック・テスト後に、実APIへ接続したWeb画面で基本導線と表示も確認します。会計記録が成功しても、外部決済の実行やメール送信まで完了したことを示すものではありません。
